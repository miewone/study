Executive answer

여섯 요소는 “업무 의미”와 “실행 권한”을 섞지 않기 위해 분리한다

핵심 답: Object Type은 규칙, Object는 실제 대상, Property는 대상의 값, Link는 대상 사이의 역할, Function은 상태를 바꾸지 않는 계산, Action은 검증된 상태 변경이다. 이 책임 분리를 지키면 LLM이나 애플리케이션이 물리 테이블을 직접 추측하지 않고도 무엇을 찾고 → 어떤 범위를 선택하고 → 무엇을 계산하고 → 무엇을 변경할 수 있는지를 안전하게 판단할 수 있다.

Link인스턴스 사이의 역할 관계

Object Type “무엇의 종류인가?” Identity, Property, Link, lifecycle의 공통 계약 테이블 구조가 곧 업무 의미가 되고 같은 개념이 중복된다.
Object “정확히 어느 대상인가?” 타입에 속하는 실제 identity-bearing 인스턴스 타입 정의만 존재하는데 실제 데이터가 있다고 오인한다.
Property “그 대상의 값은 무엇인가?” Identity·제목·시간·분류·측정·출처 값 단순 문자열까지 Object로 만들어 모델이 폭증한다.
Link “어떤 역할로 누구와 연결되는가?” 방향·cardinality·필수성·join 근거 label join, fan-out, orphan, 잘못된 국가 간 병합이 생긴다.
Function “무엇을 읽고 계산할 수 있는가?” Side effect 없는 bounded 조회·집계·감사 자유 SQL이나 숨은 계산이 정책을 우회한다.
Action “무엇을 실제로 바꿀 수 있는가?” 권한·검증·감사·보상 가능한 mutation LLM 답변이나 분석 결과가 곧바로 업무 상태를 변경한다.

Design premise

출발점은 “테이블”이 아니라 “업무 현실”이다

현재 source는 주간 이커머스 BI export 형태의 와이드 데이터다. 그러나 테이블 하나 = Object Type 하나로 복사하면, 시장·리테일러·관측값·분류값이 한 덩어리가 되고 동일한 시장과 리테일러가 모든 행에서 반복된다. 이 설계는 먼저 source row의 Grain과 반복되는 업무 명사를 분리한 뒤, 독립 identity가 필요한 대상만 Object Type으로 승격한다.

1. Grain 우선

한 행이 무엇 하나를 뜻하는지 먼저 고정한다. 현재 Overview physical Grain v1은 날짜·시장·리테일러와 다섯 source 분류의 8-field tuple이다.

2. Identity 우선

이름이나 현재 값이 아니라 불변 business ID, canonical ID, 안정적 복합키 순서로 identity를 결정한다.

3. 증거 우선

근거 없는 master·mapping·cardinality·인과관계를 만들지 않는다. 부족한 것은 BLOCKED로 남긴다.

왜 전체 설계 29개를 바로 활성화하지 않았는가

full design catalog에는 Entity, Reference, Time, Observation, Plan·Target, Workflow까지 29개 Object Type 후보가 있다. 하지만 첫 canonical release는 source evidence를 안전하게 읽고 감사하는 데 필요한 정확한 최소 closure만 채택한다. Metric 정의, canonical master, writeback authority가 없는 상태에서 전체 catalog를 seed하면 “문서에 있다”가 “실행 가능하다”로 잘못 승격되기 때문이다.

Element 01

1Object Type — 공통 규칙을 가진 업무 개념

Object Type은 클래스에 가깝다. 개별 데이터 행을 담는 그릇이 아니라, 같은 정체성 규칙과 Property, Link, 권한, lifecycle을 공유하는 업무 대상의 계약이다. 독립 조회·반복 연결·감사·선택 필요성이 강하거나, 명확한 시점·Grain·출처를 보존해야 하는 Observation일 때 Object Type으로 만든다.

Canonical 최소 release가 네 타입을 고른 이유

Market CONFIRMED

  • 시장 범위는 여러 Retailer와 Observation이 반복 참조한다.
  • countryCode라는 독립 identity가 필요하다.
  • 검색·필터·권한·통화 mapping의 기준점으로 재사용된다.

Property로 두지 않은 이유: 단순 country 문자열보다 더 긴 수명주기와 관계를 가지며, source label과 canonical Market을 구분해야 한다.

Currency CONFIRMED 의미

  • 여러 Market이 같은 Currency를 참조할 수 있는 canonical reference다.
  • 통화 코드는 Amount 행마다 복제하기보다 하나의 vocabulary로 관리해야 한다.
  • Market과의 effective-dated mapping을 명시적으로 검증해야 한다.

중요: 의미 계약은 확정됐지만 materialized master와 instance가 없어 구현·activation은 차단돼 있다.

Retailer CONFIRMED 의미

  • 표시 이름이 바뀌어도 유지되는 불변 retailerId가 필요하다.
  • Market, Observation, 향후 Plan·Target이 반복 참조한다.
  • rename·merge·split·source crosswalk를 별도 관리해야 한다.

이름을 identity로 쓰지 않는 이유: 같은 “Amazon”도 CA·DE·UK에서 서로 다른 Retailer Object일 수 있다.

WeeklyEcommerceOverviewObservation PROVISIONAL

  • source row 하나의 시점·Grain·출처·정정 증거를 보존한다.
  • 독립 lifecycle은 약해도 Observation 예외 조건을 충족한다.
  • raw retrieval과 quality audit의 root로 사용된다.

Fact row를 그대로 업무 실적으로 부르지 않는 이유: 현재는 BI export의 source evidence이며 universal KPI나 원천 거래 event가 아니다.

Element 02

2Object — 타입에 속하는 실제 업무 인스턴스

Object Type이 “Market은 countryCode로 식별한다”는 규칙이라면, Object는 그 규칙을 만족하는 Market(countryCode="<canonical-country-code>")다. 이 둘을 분리해야 타입 정의가 존재하는 것과 실제 population이 materialize된 것을 혼동하지 않는다.

비POC canonical Object 예시

아래 예시는 production 형태를 설명하는 schema example이다. 현재 운영 master와 immutable source population이 준비되지 않았으므로 실제 국가·통화·리테일러 값이나 UUID를 임의로 만들지 않는다. Placeholder가 채워지고 identity·Link gate를 통과해야 비로소 실제 canonical Object가 된다.

Element 03

3Property — Object를 설명하는 typed value

Property는 독립 대상이 아니라 Object에 귀속되는 값이다. 문자열·숫자·날짜·상태·분류·측정값을 Property로 유지하면 모델을 단순하게 유지하면서도 identity, 표시, 필터, 집계, provenance를 명시적으로 구분할 수 있다.

POC에서는 왜 13개인가

Synthetic POC는 Currency와 usesDefaultCurrency를 제외하고, source에서 직접 확인된 두 traffic count impressionCount와 clickCount를 MEASURE로 추가한다. 따라서 Market 1 + Retailer 2 + Observation 10 = 13이다. 두 값은 fixture 범위에서만 합산 가능하며 universal KPI 정의로 승격되지 않는다.

왜 54개 source field를 모두 Property로 노출하지 않는가: 최소 release의 목적은 source evidence 조회와 품질 감사다. 모든 physical column을 wildcard로 노출하면 검토되지 않은 Metric 의미, 민감한 locator, 임의 join key가 ontology surface로 새어 나온다. 따라서 명시적으로 채택한 closed Property만 반환한다.

Measure ownership

Sell-out·ROAS 값은 “그 값을 관측한 Object”의 Property다

Element 04

4Link — Object 사이의 역할이 있는 관계

Link는 단순 foreign key나 같은 문자열의 일치가 아니다. “누가 누구와 어떤 역할로 연결되는지”, “한쪽에서 몇 개까지 허용되는지”, “필수인지”, “어떤 mapping 증거로 join하는지”를 함께 정의한다. 이 정보가 있어야 agent가 안전하게 탐색하고, fan-out이나 잘못된 label join을 차단할 수 있다.

Link From → To Cardinality 왜 필요한가 실패 조건
operatesIn Retailer → Market M:1, required Retailer의 국가 범위를 label이 아니라 canonical 관계로 확정 0개·2개 이상 Market, 기간 중 mapping 불일치
usesDefaultCurrency Market → Currency M:1, required Market-scoped 값을 명시적 Currency master로 해석 승인 mapping 없음, 중복 effective mapping
observedInMarket Observation → Market M:1, required 관측 row의 시장 provenance를 typed endpoint에 연결 Source country와 Market mapping 불일치
measuredAtRetailer Observation → Retailer M:1, required 관측 row를 승인된 Retailer identity에 연결 Label-only join, cross-Market merge, crosswalk 0/N match

Link가 Property보다 안전한 이유

문자열 복제 방지

Observation마다 marketName, currencyCode를 복제하면 rename·alias·historical mapping을 일관되게 검증할 수 없다.

경로 일관성 검증

Observation.observedInMarket은 measuredAtRetailer → operatesIn으로 도달한 Market과 반드시 같아야 한다.

양방향 탐색

하나의 Link로 Retailer→Market과 Market→Retailer reverse traversal을 제공한다. reverse Link를 중복 생성하지 않는다.

관계 자체의 승격 가능성

관계에 validity·status·approval·배분율이 생기면 Link에 숨기지 않고 relationship Object Type으로 승격한다.

Synthetic POC의 Link Type은 Currency를 제외한 3개이며, materialization 목표 Link instance는 operatesIn 9 + observedInMarket 200 + measuredAtRetailer 200 = 409다. Type 수와 instance 수를 분리해 기록해야 “Link 정의가 있다”와 “실제 관계 graph가 닫혔다”를 혼동하지 않는다.

Element 05

5Function — 상태를 바꾸지 않는 조회·계산 계약

Function은 Object와 Link를 읽어 조회·집계·비교·감사·추론을 수행하지만 업무 상태를 변경하지 않는다. LLM이 직접 SQL과 산식을 만들게 하지 않고, 검토된 입력·출력·한도·lineage를 가진 named capability만 실행하게 하는 것이 목적이다.

Canonical 최소 release의 두 Function

Function Mode 책임 왜 이 두 개만 실행 가능한가
getWeeklyOverviewRows READ_ONLY 승인된 Market·Retailer·기간의 source-evidence Observation을 bounded 조회 검토된 12 Property·4 Link projection만 반환하며 Metric 해석이 필요 없다.
auditWeeklyOverviewQuality COMPUTE 같은 범위의 identity·mapping·schema·Grain 품질을 side-effect 없이 감사 읽기 기반 품질 검증이며 workflow나 source를 변경하지 않는다.

Function 경계가 강한 이유

  • countryCode, retailerId, 반개방 period를 required input으로 고정한다.
  • 최대 기간·row·scan byte·timeout으로 읽기 비용을 bounded한다.
  • 호출자가 table·column·Function·Link key 또는 자유 SQL identifier를 주입하지 못하게 한다.
  • 출력은 closed schema이며 raw 54-field wildcard, 임의 집계, dedup, latest-row 선택을 금지한다.
  • 정의된 Function과 model-visible Tool을 분리해 DRAFT·BLOCKED capability를 노출하지 않는다.

Synthetic POC의 세 Function은 무엇이 다른가

summarizeWeeklyTraffic

선택된 Market·Retailer와 기간에 대해 impression·click 합계, row count, 중복 Grain disclosure를 반환한다.

compareWeeklyTrafficContributions

두 기간의 변화와 dimension별 contribution을 비교하되 인과 원인으로 표현하지 않는다.

auditWeeklyTrafficLineage

전체 frozen profile의 schema·identity·관계·lineage와 production blocker를 감사한다.

Resolver operation은 Function이 아니다: discoverObjectTypes, discoverObjectInstances, selectObjectScope는 query-planning control plane의 내부 operation이다. 업무 데이터를 계산하는 Registry Function이나 public Tool로 세지 않는다. 이 구분은 탐색 권한과 domain 계산 권한을 분리한다.

Full catalog의 summarizeWeeklyPerformance, compareWeeklyPerformance, rankPerformanceContributionDrivers는 Metric·calendar·독립 Dimension 근거가 부족해 BLOCKED다. LLM이 raw 조회와 자체 계산으로 이 blocker를 우회해서는 안 된다.

Element 06

6Action — 권한과 감사를 거친 상태 변경

Action은 Object·Link·외부 운영 시스템의 상태를 실제로 바꾸는 명령이다. 조회와 mutation을 분리하면 read-only 분석 credential이 write 권한으로 확대되지 않고, 사용자 승인·사전 조건·감사·보상 규칙을 별도로 강제할 수 있다.

Function

“DE Amazon의 주간 traffic을 비교해줘.”

결과: 읽기·계산·설명
State change: 0

≠

LLM 제안

“이상 변화를 조사하는 것이 좋겠습니다.”

결과: 제안 텍스트
State change: 0

≠

Action

CreatePerformanceInvestigation

결과: workflow row 생성
State change: 1

왜 canonical 최소 release의 Action은 0개인가

  • 현재 source는 read-only BI/DM이며 운영 source-of-truth가 아니다.
  • Action authorization policy와 실행 주체가 준비되지 않았다.
  • Evidence resolver, write binding, audit record, rollback/compensation 계약이 닫히지 않았다.
  • 따라서 Action이나 write Tool을 노출하면 문서상 의도를 실제 권한으로 오인하게 된다.
향후 후보 Target 현재 상태 실행 전 필수 계약
CreatePerformanceInvestigation PerformanceInvestigation PROPOSED / executable=false Typed input, 대상 Object scope, 사용자 권한, evidence reference, workflow write binding, audit, rollback
Action 0은 누락이 아니라 안전 계약이다: 분석 결과가 좋아 보인다는 이유만으로 investigation 생성, 예산 변경, 승인·반려를 실행하지 않는다. write authority와 보상 경로가 준비된 후 새 immutable release에서 명시적으로 추가해야 한다.

End-to-end composition

여섯 요소는 하나의 안전한 업무 문장을 완성한다

예시 질문: “DE의 Amazon에서 2025년 10월 주간 traffic을 보여줘.”

순서 사용 요소 해결하는 내용 검증 포인트
1 Object Type DE는 Market, Amazon은 Retailer, traffic row는 Observation임을 해석 Caller-visible type과 reviewed alias만 사용
2 Object Market.DE와 DE-scoped Amazon UUID를 선택 동명 Retailer ambiguity, identity materialization, snapshot freshness
3 Link Amazon operatesIn DE인지 확인 0/N match, cross-Market label merge, path mismatch 거부
4 Property 기간, impressionCount, clickCount와 provenance projection 결정 Closed allowlist, type, null, numeric boundary
5 Function 호환되는 summary Function을 선택해 bounded read 실행 권한, 기간 한도, lineage, no-dedup disclosure
6 Action 현재는 없음. 분석 결과를 읽기 응답으로만 종료 Mutation·write credential·workflow 변경 exact 0

이 구조에서 agent는 source table 이름이나 physical column을 직접 고르지 않는다. 먼저 identity와 Link가 검증된 ResolvedObjectScope를 만들고, 그 scope와 호환되는 Function만 노출한다. Action이 필요한 요청은 별도 authorization boundary로 넘긴다.

Modeling decision guide

새 개념이 들어올 때 어디에 배치할지 판단하는 기준

독립적이고 안정적인 identity가 필요한가?
예 → Object Type 후보. 아니오 → Property 또는 계산 결과 검토.
타입에 속하는 특정 실재 대상을 가리키는가?
예 → Object. 타입 정의만 있다면 Object가 존재한다고 주장하지 않는다.
문자열·숫자·날짜·상태·분류 같은 값인가?
예 → Property. 별도 lifecycle·권한·관계가 생길 때만 Object Type 승격.
다른 Object를 반복 참조하고 역할·cardinality가 중요한가?
예 → Link. 관계 자체에 상태가 있으면 relationship Object Type 검토.
조회·필터·집계·비교·감사·추론인가?
예 → Function. 입력·출력·한도·lineage를 closed contract로 정의.
업무나 외부 시스템 상태를 변경하는가?
예 → Action. 권한·사전조건·감사·rollback 없이 실행 금지.

Objective review

성능·보안·확장성 관점의 객관적 검토

성능

장점: closed Function과 bounded input으로 scan·row·timeout을 제한하고, Object/Link index를 통해 반복 full-source lookup을 피할 수 있다.

주의: Link traversal과 effective-dated mapping이 늘면 index·pre-aggregation 전략이 필요하다.

보안

장점: 물리 identifier, 자유 SQL, unscoped enumeration, write credential을 model surface에서 제거한다.

주의: visibility filtering은 discovery 전과 Function 실행 직전에 같은 predicate로 재검증해야 한다.

확장성

장점: Object Type·Function·Action이 느슨하게 결합돼 새 vertical slice를 immutable version으로 추가할 수 있다.

주의: 모든 분류를 Object Type으로 승격하면 catalog와 crosswalk 운영비가 급증한다.
