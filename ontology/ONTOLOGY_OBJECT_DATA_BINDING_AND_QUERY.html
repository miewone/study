Executive answer

Object Type은 의미를, Mapping은 위치를, Runtime은 값을 가져오는 일을 맡는다

핵심 답: Object Type은 Identity·Property·Link·Function·Action의 업무적 모양을 정의한다. 어느 DB·테이블·컬럼에서 값을 읽는지는 Object Type 자체가 아니라 versioned Mapping 계층이 정의한다. 실제 값은 외부 DW/DM, ontology-owned master 또는 workflow store에 존재하며, Runtime adapter가 Mapping을 따라 읽고 typed Object 형태로 반환한다.

Registry contract

실제 데이터 위치는 versioned Registry graph가 안다

정확히는 Object Type 하나가 위치를 모두 들고 있는 것이 아니라, 같은 ontology version에 속한 source·asset·field·mapping row가 합쳐져 완전한 조회 계약을 만든다. Registry는 업무 데이터 자체를 저장하는 곳이 아니라 무엇을 어디서 어떻게 읽을 수 있는지를 통제하는 metadata graph다.

Registry relation 저장하는 계약 예시 역할
data_source 엔진 종류와 secret이 아닌 runtime_binding_key BIGQUERY, POSTGRESQL 등 trusted provider 선택
data_asset TABLE·VIEW·API·FILE·QUERY와 catalog/schema/asset locator 어느 BI_EXPORT 또는 master table을 읽는지 식별
data_asset_field 물리 field 이름·ordinal·type·nullability 존재하지 않거나 type이 달라진 컬럼 mapping 차단
object_type_mapping Object Type ↔ Asset, mapping type, access mode, filter plan 행, distinct projection, canonical join 또는 computed Object 생성
property_mapping Property ↔ source field 또는 expression plan impressionCount를 source impressions에 direct mapping
link_mapping Link의 from/to mapping과 resolution strategy same-source join 또는 target identity lookup
link_mapping_component 순서가 있는 from/to field equality 계약 label 추측이 아닌 검증된 join component
function_logical_plan Object·Property·Link 기준의 engine-neutral 실행 단계 필터·집계·projection 순서 고정
function_engine_override 특정 엔진의 read-only query template와 parameter schema 승인된 BigQuery/PostgreSQL 최적화 경로
왜 분리하는가: 같은 Object Type을 개발·운영 또는 국가별로 다른 Asset에 연결할 수 있고, source가 바뀌어도 업무 API를 유지할 수 있다. 또한 LLM과 일반 호출자에게 table·column·credential을 공개하지 않고 runtime provider만 물리 locator를 해석하게 할 수 있다.

Backing strategy

Object마다 실제 값이 존재하는 위치가 다를 수 있다

VIRTUAL_EXTERNAL

실제 값은 외부 DW·DM·API에 남아 있고, 조회할 때 Object 형태로 투영한다.

후보: PaidSelloutObservation, OnsiteEfficiencyObservation, TotalSelloutObservation

복제: 전체 Measure를 Registry에 복제할 필요 없음

MATERIALIZED_MASTER

Canonical identity와 lifecycle을 ontology-owned master가 저장한다.

후보: Retailer, Currency, reference vocabulary

필수: source crosswalk·validity·dedup 계약

OPERATIONAL_OWNED

상태 변경이 필요한 Object는 workflow 또는 운영 store가 소유한다.

후보: PerformanceInvestigation, MetricTargetLine

필수: Action authorization·audit·rollback

호출자는 backing strategy 차이를 직접 처리하지 않는다. 동일한 Object reference와 typed Property interface를 사용하고, Registry와 Runtime adapter가 실제 source를 선택한다.

Property value resolution

Property 값은 저장 컬럼·계산 결과·미연결 상태 중 하나다

DIRECT

실제 source field에 저장된 값을 그대로 typed Property로 읽는다.

impressionCount → source.impressions

Source type·nullability·Grain·lineage를 함께 검증한다.

EXPRESSION

승인된 expression plan 또는 Function이 조회 시 값을 계산한다.

ctr → safeDivide(clicks, impressions)

별도 저장 컬럼이 없어도 되지만 formula·scale·zero 정책이 필요하다.

UNMAPPED / BLOCKED

업무 개념은 정의됐지만 승인된 source field나 expression이 없다.

canonicalRoas → no approved mapping

현재 실행·노출하지 않고 fail closed한다.

조회 가능 조건: PropertyDefinition + ObjectTypeMapping + PropertyMapping + 승인된 DataAsset + Runtime adapter + 권한·Grain 검증이 함께 있어야 한다.

Runtime이 반환하는 것은 물리 행이 아니라 typed Object projection이다

{ "objectType": "PaidSelloutObservation", "objectRef": "<approved-object-identity>", "properties": { "paidSelloutAmount": 985000000 }, "links": { "paidSelloutObservedForRetailer": "Retailer.<id>", "paidSelloutObservedInPeriod": "BusinessPeriod.2026-W31" }, "lineage": { "ontologyVersion": "<active-version>", "mappingVersion": "<immutable-mapping-version>", "dataSnapshot": "<approved-snapshot>" } }
  • 사용자는 table·column·SQL·credential을 입력하지 않는다.
  • LLM이 source field 이름이나 join을 생성하지 않는다.
  • 결과에는 closed Property와 typed Link만 포함하고 wildcard를 금지한다.
  • 어느 ontology version·mapping·snapshot으로 읽었는지 lineage를 보존한다.

Discovery vs. measure read

Object 탐색용 정보와 대량 Measure는 따로 저장할 수 있다

Object discovery index

목적: 사용자가 선택할 Object를 빠르고 안전하게 찾는다.

저장 후보: ObjectRef, Object Type, title, 주요 Link, visibility, snapshot binding.

포함하지 않아도 되는 것: 모든 기간의 대량 Measure와 raw source payload.

Objective review

성능·보안·확장성 관점의 판단

성능

장점: Object discovery index와 Measure read를 분리하고, Function별 row·scan·timeout을 제한할 수 있다.

주의: Virtual Object를 매번 복잡한 join으로 만들면 느려질 수 있으므로 반복 경로는 View·materialized projection·cache를 검토한다.

보안

장점: 물리 locator와 credential을 model-visible interface에서 제거하고 approved mapping만 실행한다.

주의: Registry visibility와 runtime source 권한을 실행 직전에 같은 scope로 다시 검증해야 한다.

확장성

장점: Source 교체나 Fact 분리 시 Object API를 유지한 채 새 immutable mapping version으로 전환할 수 있다.

주의: Mapping이 늘어날수록 lineage·activation·compatibility test가 필수다.
